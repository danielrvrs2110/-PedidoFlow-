# PedidoFlow Tenant-First Data Model

## Purpose

This contract turns the domain overview in `PEDIDOFLOW_MASTER.md` into an
implementable Cloudflare D1 and Drizzle model. It defines ownership,
relationships, data representation, invariants, indexing, and migration
boundaries before schema code is generated.

The first database phase creates local schema and deterministic seed tooling.
It does not provision production infrastructure, implement authentication,
expose CRUD endpoints, or connect AI and messaging providers.

## Storage Conventions

### Identifiers

- Application-owned primary keys are opaque text IDs with a stable type prefix,
  generated by the server.
- IDs are never sequential or meaningful to customers.
- Tenant-owned tables use a primary `id` plus a unique
  `(organization_id, id)` key so children can enforce tenant-consistent
  composite foreign keys.

### Time

- Timestamps are UTC Unix milliseconds stored as SQLite integers.
- Server code, not the browser, supplies audit and mutation timestamps.
- Business dates such as a payment due date use ISO `YYYY-MM-DD` text when time
  of day is not meaningful.

### Money and quantity

- Money is stored as integer minor units, for example MXN 410.00 as `41000`.
- Every monetary aggregate is calculated from minor units; SQLite `REAL` is not
  used for money.
- Operational quantities use signed integer milli-units: `1250` represents
  `1.250` of the associated unit. Values shown to users are formatted at the
  boundary.
- Confidence uses integer basis points from `0` through `10000`; the visual
  layer does not own threshold definitions.

### Text and booleans

- Enums are lowercase text with database `CHECK` constraints.
- Booleans are SQLite integers constrained to `0` or `1`.
- Required user-facing names are trimmed and non-empty at the application
  boundary.
- Normalized aliases use a documented normalization function in application
  code; the raw alias is retained for display and audit.

## Authentication Boundary

Better Auth owns its user, session, account, and verification tables. Its exact
schema is generated and reviewed during the authentication milestone against
the installed Better Auth version.

The domain schema may store nullable `user_id`/`actor_user_id` text references
before authentication exists, but the first domain migration does not invent a
user table or foreign-key contract for Better Auth. `organization_members`
becomes the bridge between authenticated users and organizations. No business
query may infer organization access from a client-supplied ID.

## Core Ownership Model

```text
organization
├── organization_members
├── customers ── customer_addresses
├── products ── product_aliases
├── price_lists ── price_list_items
│                  └── customer_price_lists
├── inventory ── inventory_adjustments
├── conversations ── messages ── message_attachments
├── order_drafts ── order_draft_items
├── orders ── order_items ── order_status_events
├── payments
├── ai_processing_runs
└── audit_events
```

Every table below except Better Auth tables includes `organization_id`, or is
the organization root itself.

## Tables

### `organizations`

- `id`, `name`, globally unique normalized `slug`.
- `status`: `active` or `suspended`.
- `created_at`, `updated_at`.
- Suspension prevents new operational mutations but does not erase history.

### `organization_members`

- Composite primary key `(organization_id, user_id)`.
- `role`: `owner`, `admin`, `operator`, or `picker`.
- `status`: `active` or `invited` initially.
- `created_at`, `updated_at`.
- At least one owner is an application invariant; removing the final owner is
  never a direct database deletion.

### `customers` and `customer_addresses`

Customers contain `id`, `organization_id`, optional tenant-local `code`, `name`,
optional email and phone, `status` (`active`/`inactive`), and timestamps.
`(organization_id, code)` is unique when a code exists.

Addresses contain a label, recipient, street lines, locality, region, postal
code, country code, delivery notes, and one default-delivery flag. A composite
foreign key guarantees that the customer belongs to the same organization.
Only one default delivery address per customer is an application invariant
validated transactionally.

### `products` and `product_aliases`

Products contain tenant-unique `sku`, name, optional variant, order unit,
optional unit quantity in milli-units, optional unit measure, active flag, and
timestamps. Price does not live on the product record.

Aliases contain raw `alias`, `normalized_alias`, the product reference, source
(`manual`, `import`, or `correction`), and timestamps. The unique key is
`(organization_id, product_id, normalized_alias)`. A lookup index begins with
`(organization_id, normalized_alias)`.

### `price_lists`, `price_list_items`, and `customer_price_lists`

Price lists contain tenant-unique name, ISO currency code, active flag, and
timestamps.

Price-list items contain a product, `unit_price_minor`, `valid_from`, optional
`valid_to`, and timestamps. Customer assignments use the same effective-date
shape. Overlapping active ranges for the same organization/list/product or
organization/customer are rejected by application transactions because SQLite
cannot express the required interval-exclusion constraint directly.

Confirmed order items copy the applied price and currency. Later changes to a
price list never rewrite order history.

### `inventory` and `inventory_adjustments`

Inventory has one row per organization/product with `on_hand_milli`,
`reserved_milli`, and `updated_at`. Both quantities are non-negative and
reserved inventory cannot exceed on-hand inventory.

Every stock mutation appends an adjustment with signed `delta_milli`, reason,
source type, optional source ID, nullable actor, and timestamp. Direct inventory
updates without an adjustment in the same transaction are prohibited by the
repository layer. PedidoFlow provides simple operational stock, not ERP/WMS
synchronization.

### `conversations`, `messages`, and `message_attachments`

Conversations contain optional customer, channel (`demo`, `whatsapp`, or
`email` when supported), optional provider conversation ID, status (`open`,
`processing`, `needs_review`, or `resolved`), latest-message time, and
timestamps. Provider identity is unique within organization and channel when
present.

Messages contain conversation, direction (`inbound`/`outbound`), optional
provider message ID, message type, body, provider/delivery status, occurred
time, and created time. Attachments keep provider metadata and an R2 object key;
binary data never lives in D1. Provider message identity is idempotent and
unique within the organization when present.

### `order_drafts` and `order_draft_items`

An order draft belongs to an optional conversation and customer. It stores the
original source text, source type, status (`interpreting`, `needs_review`,
`ready`, `confirmed`, `failed`, or `discarded`), optimistic `version`, nullable
creator, and timestamps.

Draft items retain ordered text, position, optional proposed product, optional
quantity/unit/price, confidence basis points, match method (`deterministic`,
`ai`, `manual`, or `unmatched`), review flag/reason, and timestamps. Position is
unique within a draft. A draft cannot reach `ready` while a required field or
review decision remains unresolved.

Draft confirmation is a server transaction that validates the current version,
creates the confirmed order and item snapshots, appends its first status event,
and marks the draft confirmed. AI processing cannot invoke this transition
without an authenticated human action.

### `orders`, `order_items`, and `order_status_events`

Orders contain tenant-unique human-readable `order_number`, customer, optional
source draft/conversation, status, currency, optional fulfillment notes,
subtotal/total minor units, optimistic `version`, creator/confirmer, confirmation
time, and timestamps.

Allowed lifecycle values are:

```text
draft -> needs_review -> confirmed -> preparing -> ready
      -> out_for_delivery -> delivered
```

`cancelled` is terminal and requires a reason. Transition rules live in one
domain service rather than arbitrary update handlers.

Order items preserve position, optional product reference, ordered text,
SKU/name/variant snapshots, quantity milli-units, unit, unit price, line total,
and optional match/audit context. Confirmed items require all snapshots and
prices even if the catalog record is later deactivated.

Every status change appends an event containing from/to status, nullable actor,
reason/note, and timestamp in the same transaction as the order update.

### `payments`

Payments belong to an order and contain status (`pending`, `partial`, `paid`,
`overdue`, or `void`), expected and received minor units, currency, optional due
date, paid time, nullable actor, and timestamps. This is payment-state tracking,
not payment processing or accounting. Received amounts cannot be negative.

### `ai_processing_runs`

Runs belong to a draft and record internal task type, provider, model, status,
start/finish times, token counts when available, estimated cost in a declared
minor unit when available, safe error code, and timestamps. Raw secrets and
unnecessarily duplicated customer payloads are prohibited.

### `audit_events`

Audit events contain organization, nullable actor, action, entity type and ID,
safe JSON metadata, request correlation ID when available, and timestamp. They
are append-only. Metadata must not become an uncontrolled dump of messages,
credentials, tokens, or file contents.

## Tenant Isolation

- Repository and service methods require an explicit trusted organization
  context; optional organization scope is not allowed for tenant data.
- Fetch/update/delete uses both `organization_id` and resource ID.
- Child inserts use composite foreign keys `(organization_id, parent_id)` to
  reject cross-tenant relationships at the database boundary.
- Unique business identifiers begin with `organization_id` unless explicitly
  global, such as the organization slug.
- Authorization failures do not reveal whether an ID exists in another tenant.
- Tests must create at least two organizations and prove cross-tenant read,
  update, relationship, and uniqueness behavior.

## Deletion and History

- Organizations and records referenced by operational history are suspended or
  deactivated, not casually hard-deleted.
- Products, customers, price lists, confirmed orders, order items, status
  events, inventory adjustments, payments, AI runs, and audit events use
  restrictive deletion rules.
- Cascading deletion is limited to data with no independent business/audit
  meaning and must be explicitly reviewed in the migration.
- Data-retention and customer-erasure policy requires a later legal/product
  decision; this schema does not pretend that soft deletion alone solves it.

## Index Strategy

Indexes begin with `organization_id` for tenant-owned access patterns. The
initial migration covers:

- active customers/products and tenant-local code/SKU lookup;
- normalized product-alias lookup;
- current price assignment and effective item lookup;
- inventory by organization/product;
- conversations by status and latest-message time;
- messages by conversation and occurred time;
- drafts by status and updated time;
- orders by status, customer, and created time;
- status events by order and occurred time;
- payments by order/status/due date;
- audit and AI runs by entity/draft and created time.

Indexes must correspond to a named query shape. Avoid speculative duplicate
indexes and remember that every index increases D1 write/storage cost.

## Migration and Seed Boundary

- Drizzle schema is the typed source; generated SQL migrations are committed.
- Applied migrations are immutable. Corrections use a new migration.
- D1 foreign-key enforcement is enabled and verified locally.
- The first migration creates the complete domain shape above, excluding Better
  Auth-owned tables.
- Seed tooling is deterministic, idempotent for a fresh local database, and
  refuses to run against a remote database by default.
- Seed data uses unmistakable development names and at least two organizations
  so isolation tests cannot pass accidentally.
- No production D1 database, R2 bucket, account binding, or paid service is
  created during the local foundation task.

## Implementation Acceptance Criteria

- Drizzle and D1 tooling versions are pinned through the package lock.
- The generated initial migration applies to an empty local D1 database.
- Applying migrations a second time is safe.
- Drizzle schema includes checks, composite tenant foreign keys, unique keys,
  and named indexes described here.
- Automated tests prove money/quantity checks, lifecycle-relevant constraints,
  immutable price snapshots, and two-organization isolation.
- Deterministic local seed data validates representative relationships without
  pretending to be production data.
- Lint, typecheck, tests, migration generation/check, and production build pass.
- Documentation provides exact local reset, migrate, seed, and inspect commands.
