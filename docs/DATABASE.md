# Local D1 / Drizzle foundation (PF-017)

Status: integrated through PR #8; M3 completed on 2026-09-15. The four moderate
development-tooling findings below remain tracked.

## Scope and versions

`worker/db/schema/index.ts` is the typed domain schema. It implements the 22
domain tables in `DATA_MODEL.md`, including inventory adjustments, and excludes
Better Auth tables. `worker/db/schema/helpers.ts` contains common checks and
composite tenant references. There are no new HTTP routes or UI changes.

Validated on 2026-09-13 with Node 24.15.0 and npm 11.12.1; clean installation
used the required npm 11.19.1 command. Resolved dependencies: Drizzle ORM 0.45.2,
Drizzle Kit 0.31.10, Wrangler 4.131.0. The lockfile pins the complete dependency
graph; existing package versions were not upgraded. These are the stable
Drizzle npm releases selected for this task, rather than the v1 RC documented
alongside the stable API. No additional database runtime dependency is needed:
Wrangler supplies local D1/workerd through `getPlatformProxy` in tests.

Official references from implementation; D1 driver, local development and
foreign-key documentation rechecked on 2026-09-13:

- [Drizzle D1 driver](https://orm.drizzle.team/docs/sqlite/connect-cloudflare-d1):
  use `drizzle-orm/d1` with the Worker binding.
- [Drizzle generation](https://orm.drizzle.team/docs/drizzle-kit-generate):

## Reproduce from this checkout

Use Node 22+ and run these commands sequentially from the repository root:

```bash
npx -y npm@11.19.1 ci
npm run lint
npm run typecheck
npm run test
npm run build
git diff --check
npm run db:generate
npm run db:check
npm run db:reset:local
npm run db:migrate:local
npm run db:migrate:local
npm run db:seed:local
npm run db:seed:local
npm run db:inspect:local
```

`npm run test:db` runs the database suite alone. It starts one ephemeral D1
instance, applies all committed migrations, seeds two organizations, and disposes the
runtime after all tests. No development database is opened by the tests.
`vitest.config.ts` uses the Node environment and React JSX support separately
from the application Vite configuration. This avoids the Cloudflare application
plugin rejecting Vitest's injected `resolve.external` settings; D1 tests own
their runtime lifecycle. The PF-019 full suite has 97 tests, including 71
database/local-tooling tests and 8 authentication tests.

`db:reset:local` removes **only** this checkout's `.wrangler/pf017-local`
persistence. It does not migrate automatically. `db:migrate:local` applies
the PF-017 migrations plus the PF-019 auth migration; a repeated invocation prints
`No migrations to apply!`. `db:inspect:local` shows FK enforcement, FK violations,
tables, development organizations, product counts, and the migration ledger.
Expected FK outputs are `foreign_keys: 1` and an empty `foreign_key_check` result.

The dedicated `wrangler.database.json` has an unmistakable development name,
a fixed synthetic database ID and `remote: false`. It is not a deployable
production binding. The application Worker adds only Better Auth's required
`nodejs_compat` flag; it does not invent a deployable D1 database ID. A future
infrastructure task must provision and deliberately wire the real application
binding before preview or production deployment.

All reset/migrate/seed/inspect commands take **zero additional arguments**.
They fail before touching state for `--remote`, `--local`, custom configurations,
environments, persistence paths, database names, or any other extra argument.
They validate the fixed local configuration and pass explicit `--local`,
`--config` and `--persist-to` values to the installed Wrangler. They neither
create resources nor request credentials. The scripts reject symlinked managed
persistence paths and serialize use with `.wrangler/pf017-local.lock`.

Do not run a manually started workerd/Wrangler instance against that same
persistence while these commands run. The project lock covers project scripts,
not arbitrary external processes. If a process is forcibly killed, first verify
that it is stopped, then remove the empty stale lock directory with
`rmdir .wrangler/pf017-local.lock`. Never reset another checkout's persistence.

## Migrations and reproducibility

The initial SQL and `meta/0000_snapshot.json` are generated by Drizzle Kit.
The history migration was created with:

```bash
npx drizzle-kit generate --custom --name=history_guards
```

Its SQL is intentionally handwritten because Drizzle table definitions do not
represent SQLite triggers. Its journal entry and snapshot are versioned.
`db:check` validates metadata, generates against a temporary copy to detect
drift, and independently regenerates the initial SQL and schema snapshot. It
compares SQL bytes and snapshot content (excluding the random snapshot ID).
The fresh-generation comparison is intentionally specific to this initial
foundation; extend it when later schema migrations are introduced.

Do not edit migrations that have been applied. Future corrections must be new
migrations. Do not use `drizzle-kit push` for this workflow.

## Seed semantics

`worker/db/seed.sql` contains 44 inserts: one row per table per organization.
The two organizations are `org_dev_valle` and `org_dev_abastos`, visibly named
`DESARROLLO — Frutas del Valle` and `DESARROLLO — Suministros Abastos`.
Both reuse business identifiers such as `TOM-SAL-18` and `DEV-0001` to exercise
tenant-local uniqueness. IDs, timestamps, quantities and prices are fixed.

Primary-key conflicts do nothing; existing data is not overwritten. Other
unique conflicts and invalid relationships fail rather than being suppressed.
A repeated seed on the intended fixture state has identical rows across all
22 tables. Reset then migrate then seed restores the baseline. The Wrangler
file import is not promised as a whole-file transaction; after interruption,
rerunning can fill missing fixture IDs, while a reset restores exact fixtures.

The confirmed order, its event, inventory opening adjustment, attachment
metadata and AI run are explicitly development fixtures. No real file, AI call,
message delivery, user account or live order confirmation is represented.
Seed actor IDs are placeholders without an invented Better Auth FK contract.

## Enforced at the database boundary

- Tenant children have both root ownership FKs and composite
  `(organization_id, parent_id)` FKs, with `RESTRICT` on delete and update.
  Tenant rows have `(organization_id, id)` unique keys; membership uses the
  contract's composite organization/user primary key.
- SKUs, customer codes, list names, order numbers, provider identities, alias
  assignments, item positions and inventory product rows are tenant-unique.
  Nullable business identifiers retain SQLite's multiple-NULL behavior.
- Money, milli-quantities, basis-point confidence, counters and booleans have
  `typeof(...)=integer` and bounds checks, including the JS safe-integer limit.
  Money is nonnegative, ordered quantities positive, confidence 0–10000,
  reserved stock at most on-hand stock, and signed adjustments are permitted.
- Contract-defined enums use CHECKs, effective ranges have increasing endpoints,
  currencies use three uppercase ASCII letters, JSON metadata must be valid,
  and cancellation requires a nonblank reason.
- Order items require price, quantity, unit, currency, SKU and name snapshots.
  Variant snapshots can be null for products without variants.
- Audit events, order status events and inventory adjustments are append-only
  via triggers. Existing items of orders with `confirmed_at` cannot be updated
  or deleted. Confirmed order currency, totals and confirmation time cannot be
  rewritten. Price-list/catalog edits cannot change copied snapshots.

Unspecified provider vocabularies (message type, provider/delivery status,
source type, AI task type) stay text for future adapters. The initial internal
AI run states are `queued`, `running`, `succeeded`, `failed`; no provider is
connected. Timestamps, opaque ID generation, name trimming and slug
normalization remain server-boundary responsibilities.

## Query shapes and index justification

All tenant indexes start with `organization_id`. The composite identity unique
key supports safe FK targets. Additional indexes serve these query shapes:

| Tables | Supported lookup |
|---|---|
| Customers / products / price lists | Active records; tenant code/SKU/name unique lookup |
| Addresses / attachments | Children of customer/message |
| Product aliases | Normalized alias candidate matching; unique product alias |
| Price-list items / customer assignments | Effective price by list/product; current customer assignment |
| Inventory / adjustments | One stock row per product; chronological product adjustment history |
| Conversations / messages | Status plus latest message; chronological conversation messages |
| Drafts / draft items | Status plus update time; ordered positions within a draft |
| Orders / items / status events | Status or customer plus creation time; ordered items; event chronology |
| Payments | Order/status/due date and organization-wide overdue work |
| AI runs / audit events | Draft or entity plus creation time |

Unique indexes already support their leftmost prefixes; duplicate standalone
indexes are avoided. Indexes on every nullable child FK are not added without
a corresponding operational lookup; restrictive parent deletion is not the
normal business flow.

## Repository boundary and deferred invariants

`catalogRepository` only demonstrates product reads, product activation, and
alias deletion. Every lookup/mutation combines organization and resource ID;
mutations also check active organization status in the same statement. Other
organizations' IDs and absent IDs return the same `undefined`. Mutation times
are generated by the server. There are no generic unscoped CRUD helpers and
no direct stock, order, payment or audit mutation methods.

`OrganizationContext` requires organization and actor, but it is **not an
authorization mechanism**. No HTTP handler constructs it. Future authentication
must verify session, active membership and role before calling the repository;
an organization ID in a client request is never sufficient. D1 has no tenant
RLS here: raw SQL access remains privileged and can bypass repository scoping.

The following belong to future domain services and are not claimed complete:

- owner retention, role authorization, one default delivery address;
- price/assignment interval overlap checks;
- valid units, normalized inputs, currency registry validation and ID generation;
- stock adjustment plus stock update in one atomic D1 batch;
- readiness checks, optimistic concurrency and authenticated human confirmation;
- legal status transitions and cancellation/event atomicity;
- price selection, item/order currency agreement, totals, rounding and stock rules;
- locking the *set* of confirmed items against new insertions and requiring
  complete line sets at confirmation (existing snapshots are already immutable);
- payment amount/status consistency, AI execution lifecycle, audit metadata
  allowlists, retention and erasure policies.

The future confirmation transaction must create snapshots and the status event
atomically and set `confirmed_at` as the immutable boundary. This task does not
implement that service or pretend the development fixtures exercise it.

## Dependency follow-up

Before Better Auth was installed, `npm audit --omit=dev` reported zero
vulnerabilities. Better Auth 1.6.26 declares Drizzle Kit as an optional peer, so
npm 11 now classifies the existing development-only Drizzle installation as
`devOptional`: `npm audit --omit=dev` reports the same four moderate findings,
while `npm audit --omit=dev --omit=optional` reports zero. The findings remain
in Drizzle Kit's legacy `@esbuild-kit` / esbuild
chain ([advisory](https://github.com/advisories/GHSA-67mh-4wv8-2f99)). These are
development dependencies, not Worker code. No esbuild serving or Drizzle Studio
endpoint is started by this workflow. The suggested audit fix is a breaking
Drizzle downgrade, so it was not applied. Reassess when a stable tooling release
removes the chain; do not silently switch the project to an RC or downgrade.

## Better Auth identity schema (PF-019)

PF-019 pins Better Auth `1.6.26` and mounts its Web `Request` handler through
Hono at `/api/auth/*`. The Worker uses Better Auth's Drizzle adapter with D1 and
the generated SQLite schema in `worker/db/schema/auth.ts`. The schema was
generated with `npx auth@1.6.26 generate`, reviewed, and committed through the
new `0002_amusing_the_executioner.sql` migration. Applied PF-017 migrations
`0000` and `0001` and their snapshots remain byte-identical; `db:check` now
guards their SHA-256 values as well as full current migration drift.

The generated core tables are `user`, `session`, `account`, and `verification`.
Session tokens are opaque and persisted in D1; cookie caching and secondary
storage are disabled. API responses recursively remove Better Auth session,
account and provider token/password fields while retaining the HTTP-only
same-origin cookie. Tests compare session responses with the raw token stored in
D1 and cover both current-session and session-list responses. The auth schema
does not add foreign keys to PedidoFlow memberships and creates no organization
or membership during signup.

`BETTER_AUTH_URL`, `BETTER_AUTH_TRUSTED_ORIGINS`, `BETTER_AUTH_SECRET`, and
`PEDIDOFLOW_ENVIRONMENT` are validated server bindings. Trusted origins are an
explicit comma-separated allowlist and are never derived from a request.
Preview and production origins must use HTTPS. Email/password signup is enabled
only when the environment is exactly `local` or `test`; preview and production
fail closed. CSRF, Fetch Metadata, and redirect-origin checks remain enabled.
